\chapter{系统总体架构与数据库表结构}
软件架构描述了系统的顶层组织方式和结构设计，包括由哪些核心组件构成、各组件承担何种职责、模块之间如何协作，以及系统如何与数据库、缓存、中间件和外部平台交互。与代码实现细节不同，软件架构更关注系统的分层策略、模块边界、数据流向和扩展能力，目的是从宏观层面厘清“为什么这样设计”和“系统如何运转”，为后续的功能实现、数据库设计、接口定义和系统部署提供基础依据。本章将沿着“前端请求 → 后端服务 → 数据库层”这一主线展开分析。

\section{系统整体架构设计}
当前系统采用前后端分离的 B/S（Browser/Server）架构。用户通过浏览器访问系统前端页面，前端负责界面展示、交互控制、状态管理和图表可视化；后端负责认证授权、业务处理、流程流转、数据访问、缓存管理和外部系统集成。整体上，该系统属于单体式多模块业务系统。基于此，将系统自上而下纵向切分为四个相互隔离的逻辑层，各层之间严格通过接口协议进行单向依赖通信。

第一层为\textbf{前端展示层}。
负责直接与用户进行交互：向后端发起网络请求，然后在响应中拿到数据，最后完成可视化渲染。由于系统涉及大量的复杂表格和数据图。前端基于 Vue 框架的组件化思想构建单页面应用，利用其双向数据绑定特性和Element UI/Ant Design Vue组件库，快速完成“项目管理”模块中海量表单的交互与录入。在业务状态管理方面，系统采用 Vuex 进行集中式状态管理。通过 Vuex 的模块化设计（划分 account 和 setting 模块），将用户认证信息（JWT Token）、细粒度权限管控数据（Permissions）以及系统全局 UI 配置（主题色、布局风格等）进行统一存储。配合 LocalStorage 实现状态数据的本地持久化，确保用户刷新页面时状态不丢失。在业务线中（如“项目管理”及“软件风险管控”等模块），前端组件通过直接挂载 Vuex 状态进行身份识别与按钮级别的权限拦截（如动态控制操作人权限及表单默认值）；当用户进行权限切换或全局主题配置更改时，Vuex 的响应式机制能够实时捕获状态变化并通知所有嵌套子组件完成即时重绘，从而保障了多组件间跨层级数据流转的一致性与可维护性。针对 PMO 角色KPI数据查看和工时统计分析需求，引入 ECharts 数据可视化库，将后端传来的海量基础数据渲染为直观的工时占比饼图和工时趋势折线图。由 Axios 负责统一向后端发起异步的 Restful API 请求，以保障页面无刷新的流畅体验。

第二层为\textbf{安全拦截层}。
作为后端服务的统一“过滤器”，负责所有 HTTP 请求的合法性校验与细粒度的权限校验。本项目采用 Vue + Spring Boot 的前后端分离架构，传统的基于 Session 认证机制存在跨域受限和状态维持开销大的痛点。同时，作为企业级运营平台，系统必须满足内部统一身份认证（LDAP）、严格的数据越权访问拦截，以及对在线用户的实时治理（如强制下线）。为此，本系统基于 JWT + Apache Shiro + Redis 构建了一套无状态、高安全性的混合鉴权架构。登录接口首先对接企业 LDAP 服务完成统一身份核验。随后签发 JWT 实现无状态的跨域认证。为提升传输安全性，系统在 JWT 外层增加了对称加密，有效防止 Token 被网络抓包篡改。为避免复杂权限校验引发数据库 I/O 瓶颈，系统将用户角色与权限树全量预热至 Redis 缓存，在内存中完成极低延迟的权限比对，并且每次请求都要求携带 Token 前往 Redis 中校验有效性。同时将签发的 Token 与客户端 IP 地址绑定存入 Redis，一旦检测到 IP 变动或异地登录，系统将自动拦截该请求，防止令牌盗用。此外，针对 JWT 自身“一旦签发无法撤销”的技术缺陷，我们使用 Redis 追踪在线用户，管理员可通过主动清除缓存中记录与对应拼接了 IP 后缀的 Token 缓存，实现对违规用户的“强制下线”管控。所有的 HTTP 请求在触达业务层前必须经过此层。系统在此部署了 Shiro Filter Chain 拦截器，提取请求头中的 JWT 令牌进行无状态的身份验权。此外，还利用 Spring AOP 机制，使用自定义注解对登录接口实现限流。

第三层为\textbf{核心业务层}。
该层主要完成对请求的具体业务逻辑的处理，后端需快速处理复杂的工时核算与统计逻辑，同时必须解决“数据孤岛”问题，自动获取外部考勤和缺陷数据。系统基于 Spring Boot 框架搭建，系统管理模块主要负责平台基础权限与组织架构的维护；公司运营模块负责处理人员、工时等数据的流转；项目管理模块处理从立项到交付的全生命周期追踪；定时任务模块则负责后台周期性数据快照和同步任务。同时，该层还会调用外部的飞书 API 和 Jira 接口，完成考勤和缺陷数据的跨系统流转。

第四层为\textbf{数据层}。负责业务数据与系统配置的安全落地，提供海量数据的快速读写能力。在“数据持久层”，核心业务数据统一存放于 MySQL 关系型数据库，并引入 MyBatis-Plus 框架消除大量重复的单表 CRUD SQL 代码，提高开发效率。针对性能瓶颈，系统引入 Redis 分布式缓存中间件：将高频访问且极少变动的数据（如部门组织树结构），以及耗时较长的“工时统计分析”提前预热写入 Redis 内存中。当 PMO 访问看板时，数据直接从内存击中返回，从而实现毫秒级的高速响应，有效保护底层数据库。

\section{系统功能模块划分设计}
在上述分层架构的基础上，从业务维度对后端工程进行横向模块划分，将系统拆分为三个核心业务域：系统管理、公司运营管理和项目运营管理，以降低模块间的耦合度并提升代码的可维护性。在后端工程的代码组织上，如果将所有的 Controller 或者 Service 混杂在同一个包下，随着时间的推移，类越来越多，不利于开发人员进行代码的维护和拓展。因此，将工程结构划分为三个软件包：system，companyM，projectM。

\section{数据库表结构}
上述功能模块的运行均依赖于用户、角色、项目、工时等核心数据实体，为此需要设计合理的数据库表结构来持久化存储这些数据。本节首先阐述数据库设计的总体原则，然后给出系统的E-R模型及关键数据表的详细字段定义。
\subsection{数据库设计总体原则}

为保证系统在大规模数据下的稳定运行和长期可维护性，本系统在数据库结构设计时遵循以下原则。

\begin{enumerate}[label=(\arabic*)]
	
	\item 遵循数据库三范式建模，但也不是完全遵循，可以根据具体场景反范式。虽然满足三范式可以让所有基础业务表在逻辑上消除传递依赖和不必要的重复存储，以降低数据不一致风险，但对于某些高频查询且极少变动的维度信息（如部门名称、项目所属聚类名称），适当引入一些冗余的字段，可以减少多表关联查询带来的性能开销，以少量存储冗余换取查询性能的大幅提升，整体收益更高。
	
	\item 放弃物理外键，转而维护逻辑外键。建表时如果使用数据库级外键（物理外键），看起来规整，但在实际业务场景中，物理外键在增删改时会触发自动加锁和级联校验，一旦并发上来，锁竞争能把整个系统的响应速度拖慢。更麻烦的是，万一将来企业打算迁移到其他数据库，由于不同数据库对外键的支持程度不一样，还得花费大量的成本修改sql文件。而采用逻辑外键既能保留数据模型的可读性，SQL写起来也灵活，将来也便于开发人员进行维护。
	
	\item 
	重要业务表必须包含审计字段，同时采取“逻辑删除”策略。所有核心表均设置 \texttt{create\_time}、\texttt{update\_time}、\texttt{create\_by}、\texttt{update\_by} 等字段，用于记录数据的创建人与最后修改信息。同时，针对员工离职或风险关闭的场景，系统表普遍引入了 \texttt{status} 字段进行“软删除”，严禁执行 \texttt{DELETE} 物理删除语句，以防止多表联查时因关联数据丢失而大面积报错。仅仅只是多了几个字段的存储成本，就能换来数据可追溯、查询不报错的效果。
	
	\item 合理建立索引。索引的目的主要是提高数据检索速度，然而索引并非越多越好，因为其本质是用空间换时间，如果索引建立太多，不仅会占用大量空间，还会因为增删改时需要维护索引而导致性能变差。此外，我们还需明确索引适合建立在哪些字段上，通常我们会给这些类型的字段添加索引：在SQL语句的 WHERE、ORDER BY、GROUP BY 后面常出现的字段；针对复合索引，在编写SQL时要注意遵循最左前缀法则，否则会出现索引失效的情况；同时，编写SQL时应严禁在索引列上使用函数或者隐式类型转换，这同样会导致索引失效。
	
	\item 统一命名与字段类型规范。所有表名以 \texttt{t\_} 或 \texttt{tb\_} 为前缀，按业务模块统一命名；主键统一使用 \texttt{BIGINT} 自增 ID；金额类数字采用 \texttt{DECIMAL} 存储；时间字段统一使用 \texttt{DATETIME} 类型，避免在应用层再做时区转换。对于固定长度或已知长度范围的 VARCHAR 类型字段，应尽可能限制其长度。例如 VARCHAR(10) 与 VARCHAR(100)，在存储相同内容时实际占用空间相同，但排序时却差异巨大。这是因为 MySQL 在排序时，会按照字段定义的最大可能长度来估算所需内存空间。因此字段越长所需内存空间越多，就越容易因内存不足而触发磁盘排序，性能与内存排序相比差了几个数量级。
	
\end{enumerate}

\subsection{系统E-R模型设计}
在明确数据库设计总体原则之后，本节通过E-R模型梳理系统的核心数据实体及其相互关系。借助E-R图对系统进行概念建模，能够以可视化的方式呈现数据实体之间的语义关联。合理的数据库结构设计，有助于在开发前期发现潜在的数据问题，降低编码阶段的出错概率和返工成本，同时也为理解设计决策提供了清晰的分析框架。由于系统涉及的业务表较多。本文没有将所有数据库表绘制在同一张 E-R 图中，而是按照核心业务场景进行拆分。这样既可以避免整体图过于复杂，也能够更加清晰地展示不同业务域内部的数据关系。结合系统功能实现，本文主要选取 BU 工时统计、项目基本信息管理、缺陷查询与统计、重大问题管理四个核心业务场景进行 E-R 模型分析。

\begin{enumerate}[label=(\arabic*)]	
	\item BU工时统计主要用于分析各个组织部门在业务单元的工时投入情况，涉及的实体包括组织树（\texttt{tb\_org\_tree}）、员工基础信息（\texttt{tb\_emp\_baseinfo}）、项目列表（\texttt{tb\_project\_\allowbreak baseinfo\_\allowbreak new}）、工时记录（\texttt{tb\_sync\_wh}）和考勤工时（\texttt{tb\_sync\_attend\_hour}），其关系如图\ref{fig:er-org-wh}所示。
	
	\begin{figure}[htbp]

		\caption{工时E-R图}

	\end{figure}
	
	在该 E-R 模型中，\verb|tb_org_tree| 用于保存组织树结构，通过 \verb|parent_id| 与 \verb|org_id| 的自关联关系描述组织上下级层级。\verb|tb_emp_baseinfo| 用于保存员工基础信息，其中 \verb|org_id| 表示员工所属组织，\verb|uid_code| 是员工在系统中的唯一标识。工时记录表 \verb|tb_sync_wh| 存储从 Trinity 系统同步而来的员工填报工时数据，通过 \verb|uid| 与员工表中的 \verb|uid_code| 建立逻辑关联，通过 \verb|project_id| 与项目基础信息表中的 \verb|project_id| 建立逻辑关联。考勤工时表 \verb|tb_sync_attend_hour| 保存员工每日考勤工时、加班工时和填写工时等数据，同样通过 \verb|uid| 与员工表关联。
	
	该模型能够支撑 BU 工时趋势分析、BU 加班工时统计和 BU 工时占比分析等功能。系统的接口首先接收年月、组织ID作为参数，根据组织树获取目标部门下的员工范围，然后根据员工范围查询指定时间范围内的工时记录，并结合项目所属 BU 字段完成按 BU 的聚合统计。同时，通过考勤工时表中的加班字段，可以进一步计算某个 BU 的加班投入情况以及近几个月的工时趋势。
	
	\item 项目基本信息管理是项目运营管理模块的基础，其数据模型围绕项目主数据展开，并关联项目交付历史、项目里程碑和项目负责人等信息，涉及的实体包括员工信息、项目基本信息、交付历史（\verb|tb_project_delivery_history|）和里程碑（\verb|tb_project_milestone|），其关系如图\ref{fig:er-project}所示

	\begin{figure}[htbp]
		\centering
		\includegraphics[width=0.7\linewidth]{imgs/ER图-项目代码.png}
		\caption{项目基本信息E-R图}
		\label{fig:er-project}
	\end{figure}
	
	项目基础信息表 \verb|tb_project_baseinfo_new| 是该模型中的核心实体，用于保存项目编号、项目名称、项目状态、项目级别、所属 BU、项目类型、客户名称、南京项目经理、当前里程碑和近期交付阀点等信息。员工基础信息表 \verb|tb_emp_baseinfo| 通过 \verb|uid_code| 与项目表中的 \verb|nj_pm_id| 建立逻辑关联，用于描述项目与南京项目经理之间的责任关系。
	\verb|tb_project_delivery_history| 用于保存项目近期交付内容的修改历史。当项目周报中的近期交付内容或交付日期发生变化时，系统会将修改前后的内容、修改时间以及操作人记录到该表中，从而实现项目交付信息的历史追溯。该表通过 \verb|project_id| 与项目基础信息表关联。\verb|tb_project_milestone| 用于记录项目 M3、M3.1、M3.2、M3.3 等关键阶段的计划时间和实际时间，通过 \verb|project_name| 与项目基础信息表形成逻辑关联。
	通过该 E-R 模型，系统能够支持项目基础信息分页查询、组合筛选、项目信息维护、里程碑维护和周报交付历史追踪等功能。
	
	
	\item 缺陷查询与统计模块需要整合来自 Trinity、Jira 和 BugClose 等多个缺陷平台的数据，并在此基础上支持项目维度和项目聚类维度的缺陷统计分析。其关系如图\ref{fig:er-bug-cluster}所示。
	
	\begin{figure}[htbp]
		\centering
		\includegraphics[width=0.7\linewidth]{imgs/ER图-缺陷聚类.png}
		\caption{缺陷聚类E-R图}
		\label{fig:er-bug-cluster}
	\end{figure}
	
	在该模型中，\verb|tb_project_baseinfo_new| 仍然作为项目主数据表，用于提供项目编号、项目状态、所属 BU 和项目负责人等基础信息。\verb|tb_sync_bug| 用于保存从 Trinity 系统同步的缺陷数据，包括缺陷记录 ID、工作项 ID、缺陷编号、缺陷状态、责任人、所属项目、创建时间和关闭时间等字段。\verb|tb_sync_jira| 用于保存从 Jira 系统同步的问题数据，包括 Jira 问题编号、问题状态、经办人、报告人、创建时间和关闭时间等信息。\verb|tb_sync_bugclose| 用于保存从 BugClose 系统同步的缺陷数据，包括 BugClose 缺陷 ID、缺陷编号、缺陷状态、责任人、所属项目和更新时间等字段。三类缺陷表均通过项目编号或项目名称与项目基础信息表建立逻辑关联。
	
	此外，系统使用 \verb|tb_project_cluster| 表维护项目与项目聚类之间的对应关系，使用 \verb|tb_project_cluster_user| 表维护项目聚类与 SWPM 负责人之间的对应关系，使用 \verb|tb_bug_cluster_daily_snapshot| 表保存项目聚类每日缺陷快照。通过这些表，系统可以按项目群或项目聚类维度统计未关闭缺陷数量、新增缺陷数量、关闭缺陷数量和关闭率等指标。该设计能够满足管理人员从单项目维度和项目群维度分析质量风险的需求。
	
	\item 重大问题管理模块用于记录项目研发和交付过程中出现的关键质量问题、交付风险和客户关注问题，其 E-R 模型如图\ref{fig:er-serious-problem}所示。
	
	\begin{figure}[htbp]
		\centering
		\includegraphics[width=0.7\linewidth]{imgs/ER图-重大问题.png}
		\caption{重大问题E-R图}
		\label{fig:er-serious-problem}
	\end{figure}
	
	该模型中，\verb|tb_project_serious_problem_new| 是重大问题管理的核心实体，用于保存重大问题编号、问题单号、项目名称、南京项目经理 UID、项目所属 BU、根因涉及部门、问题状态、计划解决日期、实际解决日期和创建时间等信息。项目基础信息表 \verb|tb_project_baseinfo_new| 通过项目名称与重大问题表建立逻辑关联，用于说明重大问题所属项目。员工基础信息表 \verb|tb_emp_baseinfo| 通过 \verb|uid_code| 与重大问题表中的 \verb|swpm_id| 建立逻辑关联，用于标识重大问题对应的南京项目经理。员工表又通过 \verb|org_id| 与组织表 \verb|tb_org_tree| 关联，从而可以进一步追溯问题涉及人员所属组织。
	
	通过该 E-R 模型，系统能够支持重大问题分页查询、新增、编辑、详情查看、状态跟踪和数据导出等功能。重大问题表不仅记录问题本身，还记录问题所属项目、责任人、根因部门和计划解决时间等关键管理信息，因此能够为项目复盘、质量改进和管理层决策提供数据依据。
	
\end{enumerate}

整体来看，四组E-R图分别从工时、项目、缺陷和重大问题四个维度，把系统的核心数据实体及其关联关系固定下来。建模过程遵循数据库设计总体原则。后续各功能模块的详细设计，均围绕本节E-R模型展开。
