\chapter{需求分析}
需求分析是软件工程生命周期中至关重要的一个环节，它通过系统性地识别和梳理，将用户、业务方的期望和业务场景中的实际问题，转化为清晰、可执行、可验证的规格说明。这一过程从根本上决定了系统建设的边界、方向与最终交付的业务价值，是连接抽象业务需求和具体技术实现的桥梁。本章将紧密围绕企业搭建数字化运营平台的需求展开，从普通用户、项目经理、部门经理的视角出发，详细剖析系统在各大业务模块中的功能性需求，并明确界定系统在性能、健壮性与易用性等方面的非功能性需求，为后续的系统设计和开发工作提供坚实的依据。

\section{系统总体需求概述}

本系统面向企业中的软件项目管理场景，服务于汽车电子软件领域的数字化运营管理系统，旨在构建一个覆盖从项目立项、过程跟踪、质量管控到售后分析的综合性项目管理平台。系统应支持项目从基础信息维护、软件集成发布管理、风险管理、缺陷管理、发布计划、重大问题管理、项目横展流转到售后问题管理与三方测试报告归档等全过程管理，同时还要提供项目总览、工时管理、KPI数据管理、组织架构管理和员工信息管理等。

前端基于 Vue 实现交互页面，后端基于 Spring Boot 提供 RESTful 接口。用户可通过浏览器进行访问，通过统一登录界面，登录后系统根据用户角色与菜单权限动态加载可访问功能。系统需要对不同用户提供差异化操作权限，保证部门经理、项目经理、普通员工和系统管理员能够在各自职责范围内完成业务操作。系统还应具备数据查询、数据维护、流程流转、统计分析、导出、日志审计、消息提醒和外部系统集成等能力。
	
从业务目标上看，本系统需要解决传统项目管理中数据分散、流程跟踪困难、项目风险缺乏闭环、缺陷与工时统计不及时、权限管理不统一等问题；从技术目标上看，系统需要保证功能完整、权限清晰、数据可靠、交互友好，并能够满足企业内部多角色、多模块、多维度统计分析的应用需求。从系统功能架构来看，整体业务可划分为三大模块：承担认证授权、动态菜单、日志审计等基础能力的\textbf{系统管理模块}，涵盖员工档案、组织架构、KPI考核及工时管理的\textbf{公司管理模块}，覆盖软件研发流程（立项→规划→开发→测试→发布→售后）的\textbf{项目管理模块}。

由于整个平台业务链路较长、工程体量庞大。本次毕业设计课题中，我主要负责一部分功能的开发，具体包含：\textbf{公司运营管理模块中的部门投入BU工时分布}、\textbf{项目管理模块下的项目基础信息管理、缺陷管理、重大问题管理}。项目信息的维护对应项目立项阶段，项目经理在系统中登记项目基本信息，包括项目名称、所属平台、项目经理、所属BU、客户信息等，后续所有管理活动都以这些信息为基础。项目在系统中完成立项登记后，就进入版本规划与范围管理阶段，软件项目经理制定发布计划并创建软件版本，将需要修复的问题从Trinity、BugClose、Jira等外部平台导入为版本需要解决的问题清单，开发人员完成代码修复后依次经过代码评审、分支合入、点检测试和PTV产品测试验证四个质量环节，全部通过后由质量门禁统一校验，通过则冻结版本并提交集成版本确认，确认接受后正式发布；在此过程中，缺陷数据从多个外部系统持续同步并按项目、集群、时间维度进行统计分析和每日快照采集，当某个项目的缺陷可能波及其他项目时触发横展流程，由项目经理、开发、测试三角色协同排查其他同平台、同类型的项目是否存在相同问题，如果存在就把问题同步扩散过去。这是汽车行业质量管理体系中的标准做法，确保一个问题被发现后不会在其他项目中重复遗漏；同时项目经理可在任意阶段登记软件风险，风险通过责任人处置、项目经理审核、超期自动标记的流转机制和定时飞书提醒实现闭环管理，问题较大且已发生的风险可升级为重大问题并推送给管理层；版本发布后进入售后阶段，系统跟踪24小时响应率和30天修复率等SLA指标，直至所有版本发布、所有风险和问题闭环、售后可控时项目正式完结，整个过程中的里程碑变更、Scope操作历史、缺陷快照、风险处置记录和横展流转记录全部留存为企业的管理数据资产，便于公司运营管理模块进行相应的分析，比如工时管理，KPI数据统计。

通过了解整个系统的总体需求之后，针对前面提到的BU工时投入分析、项目信息管理、重大问题管理及缺陷管理等功能模块，系统主要涉及普通员工、软件项目经理和部门经理三类核心角色。下文将结合用例图来展示各参与者在系统中的用例和功能性需求：

\section{功能性需求}
在前一节中，需求调研主要从不同系统参与者的视角出发，梳理了各角色的宏观用例边界。但是一个用例可能在多个参与者中都会出现。因此，本节将功能需求的划分依据从“面向参与者视角”转换为“面向业务领域视角”。遵循高内聚、低耦合的模块化原则，将需要落地的功能性需求重新划分为以下三大类：\textbf{公司组织与工时统计分析需求}、\textbf{软件项目生命周期管理需求}，以及\textbf{自动化度量需求}。

\subsection{部门投入BU工时统计需求分析}
BU工时投入分析模块旨在为部门经理提供下属员工在各BU（Business Unit）上工时分布的全景视图，为人力资源调配与项目成本核算提供数据支撑。该模块仅涉及部门经理一类参与者。如图\ref{fig:bu-usecase}所示，系统需要提供按年月和组织树两个维度的工时数据检索能力，支持以饼图形式呈现部门整体的BU工时分布情况。同时，系统需要支持对特定BU的工时数据进行下钻分析，提供总工时、平均工时和加班工时等基础统计指标的计算能力，并能够生成近六个月的工时趋势图，以便识别工时投入的变化规律与异常波动。

\subsection{项目信息管理需求分析}
项目信息管理模块需要支持项目经理、部门经理和普通用户三类角色对项目基本信息和里程碑计划的差异化访问。如图\ref{fig:project-usecase}所示，该模块可划分为项目基本信息和里程碑计划两个子域。在项目基本信息方面，系统需要支持项目信息的新增、编辑、查询和导出能力，其中项目经理拥有完整的写权限，部门经理和普通用户仅具备只读权限。在里程碑计划方面，系统需要支持项目周报的填写、修改和查询，以及交付历史的查看，确保各角色能够在各自权限范围内获取所需的项目进度信息。

\subsection{缺陷管理需求分析}
缺陷管理模块需要解决企业内部缺陷数据分散在多个异构平台中的问题，实现缺陷信息的统一归集与聚类分析。如图\ref{fig:defect-usecase}所示，该模块的用例可归纳为缺陷查看与项目聚类管理两大部分。在缺陷查看方面，系统需要对接Trinity、Jira和BugClose三个外部缺陷跟踪平台，将分散的缺陷数据统一汇总，并支持按项目、集群、时间等多维度进行条件筛选和详情查看，三类角色均可使用该能力。在项目聚类管理方面，系统需要支持项目聚类的增删改查操作，并提供聚类下项目列表和缺陷详单的查看能力；当缺陷数量达到预警阈值时，系统需要具备通过飞书向相关人员发送预警消息的能力。此外，系统还需要支持缺陷数据的Excel导出，便于线下分析和汇报。

\subsection{重大问题管理需求分析}
重大问题管理模块需要对项目中出现的高影响风险问题提供从登记、跟踪到闭环处置的全流程管理能力。如图\ref{fig:critical-usecase}所示，系统需要支持重大问题的新建、编辑、查询和导出功能，其中编辑功能需要涵盖根因分析、关闭信息填写和问题上升标记三种处置动作。在通知机制方面，系统需要在问题新建或上升时具备通过飞书卡片消息向管理层推送通知的能力。在监督层面，系统需要支持重大问题列表查看、统计图表展示和数据导出，并支持在需要时主动触发飞书催办。此外，当重大问题需要横向扩散时，系统需要支持在问题关闭阶段将横展信息同步推送到其他可能存在相同风险的项目中，确保问题不被遗漏。该模块涉及部门经理、项目经理和普通用户三类参与者，如图\ref{fig:critical-usecase}所示。

\section{非功能性需求}
前文主要对系统的核心业务用例和功能流转进行了梳理。但在实际的企业生产环境中，除了要满足基础的业务逻辑外，系统还必须具备在长周期运营与高频使用中的可用性与可靠性，因此，在实际编码之前，本平台还需要满足以下几个关键的非功能性指标。

\subsection{性能与响应时间要求}
按照汽车软件研发团队的规模推算，系统上线后，底层的工时流水记录和历史缺陷明细表的数据量会在短时间内快速增长，导致单张数据表的体积非常大。这就要求系统在处理涉及多表关联和分组聚合统计时，不能出现严重的慢查询。特别是对于前端首页通过 ECharts 渲染的 BU 工时看板和项目健康度图表，规定相关数据接口的响应时间必须控制在用户可接受的范围以内。如果因为底层数据量过大导致页面出现长达几秒的“白屏”，或者直接抛出请求超时异常，是实际业务无法接受的，因为这非常影响用户的体验。

\subsection{定时任务与外部接口的容错性}
由于该项目的后端设有定时任务，需要定时调用外部的飞书 API 来向满足条件的用户发送飞书卡片进行催办。但在真实网络环境下，第三方接口随时都可能出现限流、网络波动或定时任务运行出错。因此，系统设计时必须考虑相应的容错处理。具体来说，当调用飞书接口超时或失败时，当前任务线程不能直接崩溃，同时，涉及业务变更的数据库操作必须触发事务回滚，防止产生脏数据。此外，系统需要把这类外部调用异常的堆栈信息完整地输出到日志文件中，并在连续失败时主动向管理员发送告警，以便人工介入排查。

\subsection{接口的安全性、健壮性}
Web 应用开发的一个基本原则是“永远不要相信前端传来的数据”。为了防止非法参数引发后台的空指针异常或越权漏洞，所有 Controller 层的入口都必须接入严格的参数校验逻辑，把无效请求直接挡在业务代码之外，降低系统不必要的运算消耗。另一方面，考虑到高并发场景，一些恶意查询或者异常前端代码会频繁查询数据库中不存在的数据，就会导致 Redis 缓存永远无法命中，所有的请求都越过缓存这道防线到达底层数据库，极易引发数据库连接池耗尽甚至宕机。因此，需要采取具体的策略来进行防范，比如最简单的操作就是缓存一些空对象，并设置合适的过期时间。

\subsection{交互体验与易用性}
由于该运营平台的使用者涵盖了从普通外包测试员工到高层 PMO 经理，各自的使用习惯差异很大，这就要求前端界面不能设计得过于繁琐。前端界面需采用现代化的扁平化设计与组件化交互规范，降低操作门槛。特别是在处理含有几十个字段的工时填报表单或缺陷长列表时，必须做好数据的异步加载、分页以及按钮的“防抖”处理（防止用户手抖连续点击提交）。当数据保存成功或后台校验失败时，系统必须通过全局的消息组件给出明确的中文提示，避免给用户造成“点不动”或“系统卡死”的错觉。

\section{本章小结}
本章围绕企业数字化运营平台的建设目标，从总体需求、功能性需求和非功能性需求三个层面，对系统进行了全面梳理与深度分析。首先从普通员工、项目经理、部门经理等核心用户的视角出发，分析出他们各自的需求。在此基础上，将待实现的功能需求按照业务领域重新聚合，同时从性能、容错、安全与易用性等角度提出了系统在高并发、大数据量场景下的非功能约束。下一章将基于此需求规格，通过描述系统的概要设计来阐述系统的整体架构设计。
