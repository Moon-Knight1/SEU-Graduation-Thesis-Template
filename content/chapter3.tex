\chapter{需求分析}
需求分析是软件工程生命周期中至关重要的一个环节，它通过系统性地识别和梳理，将用户、业务方的期望和业务场景中的实际问题，转化为清晰、可执行、可验证的规格说明。这一过程从根本上决定了系统建设的边界、方向与最终交付的业务价值，是连接抽象业务需求和具体技术实现的桥梁。本章将紧密围绕企业搭建数字化运营平台的需求展开，从普通用户、项目经理、部门经理的视角出发，详细剖析系统在各大业务模块中的功能性需求，并明确界定系统在性能、健壮性与易用性等方面的非功能性需求，为后续的系统设计和开发工作提供坚实的依据。

\section{总体需求}

本系统面向企业中的软件项目管理场景，旨在构建一个集项目管理、质量风险管控、人员组织管理、工时统计分析和系统权限管理于一体的综合性项目管理平台。系统应支持项目从基础信息维护、Scope 管理、风险登记、缺陷统计、发布计划、周报维护、横展问题流转到售后与测试报告归档等全过程管理，同时为管理人员提供项目总览、工时分析、KPI 统计等数据支撑能力。

系统采用 B/S 架构，前端基于 Vue 实现交互页面，后端基于 Spring Boot 提供 RESTfull 接口。用户通过统一登录入口进入系统，登录后系统根据用户角色与菜单权限动态加载可访问功能。系统需要对不同用户提供差异化操作权限，保证 PMO 经理、项目经理、开发人员、测试人员、普通员工和系统管理员能够在各自职责范围内完成业务操作。系统还应具备数据查询、数据维护、流程流转、统计分析、导出、日志审计、消息提醒和外部系统集成等能力。

从业务目标上看，本系统需要解决传统项目管理中数据分散、流程跟踪困难、项目风险缺乏闭环、缺陷与工时统计不及时、权限管理不统一等问题；从技术目标上看，系统需要保证功能完整、权限清晰、数据可靠、交互友好，并能够满足企业内部多角色、多模块、多维度统计分析的应用需求。从总体业务版图来看，系统横跨了几大功能领域：负责权限管理与组织架构的\textbf{系统管理模块}、面向人员档案与成本核算的\textbf{公司管理模块}、覆盖软件研发流转的\textbf{项目管理模块}。

由于整个平台业务链路较长、工程体量庞大，本次毕业设计课题中，我主要负责一些业务层面的开发，具体包含：\textbf{公司管理模块中的部门投入BU工时分布}、\textbf{项目管理模块（涵盖项目基础信息、缺陷查询、重大问题管理、软件项目周报以及项目健康模型）}。
我负责的这几个模块并不是完全孤立的，而是与系统其他部分具有一定的协同联系。比如，我的业务模块在底层依赖于“系统管理”模块提供的权限校验功能。用户的每次网络请求，都必须在请求头中携带登录时颁发给他的令牌，在拦截器这里通过安全框架 Shiro + JWT 鉴权组件来校验令牌的有效性，并结合高级数据范围权限来严格隔离不同角色的数据查看/修改范围；另一方面，我所开发的缺陷查询和项目健康模型，它们的数据来源是靠系统的定时任务执行，从Trinity、Jira等平台拉取增量数据并写入本地数据库。此外，在重大问题管理这个模块中，对于一些滞留的问题，需要通过定时任务扫描，并通过封装的飞书API 发送卡片消息提醒。
通过了解整个系统的总体需求之后，再结合对软件研发实际管理流程的调研发现，传统的管理方式主要依赖人工统计和多系统切换。为规范管理流程并提高数据统计的准确性，本人负责的核心子系统主要面向三类核心用户角色提供服务，不同角色的业务侧重点与系统用例各不相同：


\textbf{普通员工：} 
作为数字化平台的使用者，系统的主要目的是尽可能降低其操作负担，便于他进行信息查询，其主要用例是个人基本信息的维护，查看项目基本信息。

\section{功能性需求}
在前一节中，需求调研主要从不同系统参与者的视角出发，梳理了各角色的宏观用例边界。然而，一个用例可能在多个参与者中都会出现（例如：所有参与者都可以查看项目基本信息，项目经理、部门经理都能查看项目重大问题等），若继续沿着“面向角色”的维度进行功能切分，会导致内容上的重复性。因此，为了更好地衔接后续的数据库表结构设计与代码落地实现，本节将功能需求的划分依据从“面向参与者视角”转换为“面向业务领域视角”。遵循高内聚、低耦合的模块化原则，本课题将需要落地的功能性需求重新划分为以下三大类：\textbf{公司组织与工时统计分析需求}、\textbf{软件项目生命周期管理需求}，以及\textbf{自动化度量需求}。

下文将按照这一业务领域划分，对各子系统下的具体功能边界进行详细的规格说明。

\subsection{公司组织与工时统计分析需求}
该部分需求旨在建立企业的人力资源基座并精准核算研发项目的投入的人力成本。

\begin{enumerate}[label=(\arabic*)]
	\item \textbf{员工基本信息管理功能：}系统需提供员工数字档案的统一维护入口，支持员工信息的增、改、查操作；为适应企业庞大的人员基数，必须支持按姓名、工号等关键字段进行组合检索及分页显示功能。
	\item \textbf{投入 BU 工时统计分析功能：}打破传统的单纯出勤记录模式，要求员工的工时必须精准挂载到具体的业务线（BU）或项目编号上。后台服务需根据前端传入的“年-月”时间、部门 ID 等参数，执行复杂的 SQL 多表联合和分组聚合操作，计算出各业务线（BU）、平均工时和加班工时。当用户点击某个具体的BU模块后，后端会查询近六个月该部门投入在该BU的工时趋势，前端则依托 ECharts 等图表组件，将这些枯燥的汇总数字动态渲染成直观的折线趋势图和投入占比饼图。
	
\end{enumerate}

\subsection{研发项目生命周期管理需求}
该部分需求旨在打通研发各环节的信息孤岛，将零散的项目立项、代码缺陷和交付风险集中到一个后台进行统一纳管。

\begin{enumerate}[label=(\arabic*)]
	\item \textbf{项目基本信息管理功能：}系统需支持查看、新增、编辑项目基本信息；支持按日期范围、项目等级、项目状态等条件进行多维筛选和分页查询。
	\item \textbf{缺陷统计查询功能：}目前公司研发团队同时在使用 Trinity、Jira 和 Bugclose 三个异构系统记录代码缺陷，开发人员来回切换系统非常低效。因此，系统后台需设计基于 Cron 表达式的定时任务，定期调用 API 接口从这三源缺陷库拉取增量 Bug 数据并写入本地数据库。在前端界面进行分页查询，但由于缺陷表的数据量会随着时间的推移变得较大，这就会出现查询偏移量较大导致的深度分页问题，进而引发分页查询接口的性能较低。因此，该分页接口需专门进行 SQL 优化（如采用覆盖索引结合延迟关联的方法）以保障查询响应时间。此外，用户还可以按日/月/时间段统计并将数据导出为表格文件。
	\item \textbf{重大问题管理功能：}针对影响项目交付影响较大的风险，系统提供专项的闭环追踪机制，实现从发现、分析到消除的全过程记录。提供重大问题的增、删、改、查及 Excel 导出闭环操作；为了提升问题解决的响应速度，当重大问题被触发或滞留时，系统需自动调用飞书 API 向首问责任人、最终责任人及根因涉及部门的负责人推送定制化的飞书卡片消息，以提醒相关责任人及时采取措施进行处理。
	\item \textbf{软件项目周报管理功能：}系统需支持分页查询项目周报列表，允许 SPM 查看及修改项目的里程碑进度和项目交付阀点，系统需在底层记录每一次提交的快照版本，以便后期进行进度对比，保证交付过程的有迹可循。
	
\end{enumerate}

\subsection{自动化度量需求（健康度模型评估）}

在传统的研发项目管理中，缺陷往往局限于单一项目维度维度进行追踪，但是高层领导往往不关心单个项目底层 Bug 的修复细节，而是需要看几十个项目组成的“项目群”整体缺陷解决情况。对此，我们开发该功能模块来提供高于单一项目的“项目群（聚类）”维度的质量统揽能力。系统可以自定义项目聚类名称，并在改聚类下添加同一个业务线下的项目，然后统计同一聚类下所有相关项目的缺陷指标，如昨日未解决、今日未解决等，通过对这些指标进行加权计算与动态分析，最终客观输出项目的健康度定级，并提供自动预警机制，为高层管理者提供一站式的质量概览数据。

\section{非功能性需求}
前文主要对系统的核心业务用例和功能流转进行了梳理。但在实际的企业生产环境中，除了要满足基础的业务逻辑外，系统还必须具备在长周期运营与高频使用中的可用性与可靠性，因此，在实际编码之前，本平台还需要满足以下几个关键的非功能性指标。

\subsection{性能与响应时间要求}
按照汽车软件研发团队的规模推算，系统上线后，底层的工时流水记录和历史缺陷明细表的数据量会在短时间内快速增长，导致单张数据表的体积非常大。这就要求系统在处理涉及多表关联和分组聚合统计时，不能出现严重的慢查询。特别是对于前端首页通过 ECharts 渲染的 BU 工时看板和项目健康度图表，规定相关数据接口的响应时间必须控制在用户可接受的范围以内。如果因为底层数据量过大导致页面出现长达几秒的“白屏”，或者直接抛出请求超时异常，是实际业务无法接受的，因为这非常影响用户的体验。

\subsection{定时任务与外部接口的容错性}
由于该项目的后端设有定时任务，需要定时调用外部的飞书 API 来向满足条件的用户发送飞书卡片进行催办。但在真实网络环境下，第三方接口随时都可能出现限流、网络波动或定时任务运行出错。因此，系统设计时必须考虑相应的容错处理。具体来说，当调用飞书接口超时或失败时，当前任务线程不能直接崩溃，同时，涉及业务变更的数据库操作必须触发事务回滚，防止产生脏数据。此外，系统需要把这类外部调用异常的堆栈信息完整地输出到日志文件中，并在连续失败时主动向管理员发送告警，以便人工介入排查。

\subsection{接口的安全性、健壮性}
Web 应用开发的一个基本原则是“永远不要相信前端传来的数据”。为了防止非法参数引发后台的空指针异常或越权漏洞，所有 Controller 层的入口都必须接入严格的参数校验逻辑，把无效请求直接挡在业务代码之外，降低系统不必要的运算消耗。另一方面，考虑到高并发场景，一些恶意查询或者异常前端代码会频繁查询数据库中不存在的数据，就会导致 Redis 缓存永远无法命中，所有的请求都越过缓存这道防线到达底层数据库，极易引发数据库连接池耗尽甚至宕机。因此，需要采取具体的策略来进行防范，比如最简单的操作就是缓存一些空对象，并设置合适的过期时间。

\subsection{交互体验与易用性}
由于该运营平台的使用者涵盖了从普通外包测试员工到高层 PMO 经理，各自的使用习惯差异很大，这就要求前端界面不能设计得过于繁琐。前端界面需采用现代化的扁平化设计与组件化交互规范，降低操作门槛。特别是在处理含有几十个字段的工时填报表单或缺陷长列表时，必须做好数据的异步加载、分页以及按钮的“防抖”处理（防止用户手抖连续点击提交）。当数据保存成功或后台校验失败时，系统必须通过全局的消息组件给出明确的中文提示，避免给用户造成“点不动”或“系统卡死”的错觉。

\section{本章小结}
本章围绕企业数字化运营平台的建设目标，从总体需求、功能性需求和非功能性需求三个层面，对系统进行了全面梳理与深度分析。首先从普通员工、项目经理、部门经理等核心用户的视角出发，分析出他们各自的需求。在此基础上，将待实现的功能需求按照业务领域重新聚合，同时从性能、容错、安全与易用性等角度提出了系统在高并发、大数据量场景下的非功能约束。下一章将基于此需求规格，通过描述系统的概要设计来阐述系统的整体架构设计。
